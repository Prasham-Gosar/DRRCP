Disaster Relief Operational Narrative

How 10 distributed computing concepts solve real-time post-disaster challenges

In an active earthquake and flood disaster zone, terrestrial communications and power grids are severed. Autonomous edge nodes (ground stations, emergency relay towers) and UAV drones must coordinate emergency operations under volatile network partitions, variable battery levels, and intermittent coordinator connectivity.

Phase 1: Discovery & Sync
UAV and Edge nodes register with the Cluster Coordinator via Java RMI (Exp 1), send scheduled heartbeats on a 4-thread pool (Exp 2), and synchronize clocks using Cristian's algorithm with RTT compensation (Exp 3).
Phase 2: Partition & Consensus
When physical debris creates network partitions (Exp 3), isolated clusters immediately hold Bully or Ring elections (Exp 4). Concurrent status updates are merged upon healing using Vector Clocks and CRDT Set Union (Exp 5).
Phase 3: Compute, Comms & HPC
Rescue tasks are balanced by effective capacity (Exp 6), regional logs are aggregated with Apache Spark (Exp 7), coordinators replicate state for crash failover (Exp 8), alerts broadcast MPI-style (Exp 9), and risk matrices multiply in parallel (Exp 10).

Team Ownership & Package Structure

Responsibilities: Exp 1, 2, 3, RMI Registry (1099), heartbeat thread pool, Cristian clock sync, network partition controls, central EventPublisher, ScenarioRunner.

Packages: com.drs.consensus, com.drs.faulttolerance
Responsibilities: Exp 4 (Bully/Ring election), Exp 5 (Vector Clocks & CRDT state reconciliation), Exp 8 (Primary-Backup state replication and failover).
Parth (Compute & Big Data Analytics)
Packages: com.drs.compute, analytics-spark

Packages: com.drs.comm, static/
